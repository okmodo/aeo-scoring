# Isolated Cloudflare CPU pilot results

On 2026-11-05, after independently reviewed bundles and successful hosted preflights, the coordinator ran fixed synthetic workloads in a new isolated Pages project with a new D1 permit database, configured Worker CPU limit 10 ms and `fail_open: false`. The [retained observation record](../evals/changes/phase-2-closure/cpu-observations.json) contains deployment identities, exact input hashes, attempts, request IDs, matched logs, quota-query failures, inventories and cleanup. Two initial project-creation attempts failed because production and preview `fail_open` values differed; no pre-existing project was changed. The first benchmark request returned 404 before consuming a permit; the separately reviewed [runtime correction](phase-2-cpu-runtime-correction.md) preserved that failure and reduced the remaining coordinator request budget to 29.

The coordinator made **26 HTTP requests total**: the initial 404 and 25 corrected requests, with no coordinator retries. The corrected run returned HTTP 200 for 8 of 8 small and 10 of 10 medium requests, and for 6 of 7 large requests. The seventh large request returned HTTP 503 with a resource-limit message; the run stopped at that first non-success and the oversized-error workload was not attempted. The D1 balance fell from 30 to 5, consistent with 25 admitted workloads; expiry was not extended. The failed large request had no matching real-time invocation event, so its specific CPU-versus-memory cause is unknown.

Cloudflare real-time logs yielded 11 request-ID-matched invocation CPU values, in milliseconds: small **3, 4, 4, 4, 6, 6, 8, 14** and medium **51, 54, 61**. No large-request CPU value was matched. These measurements include authentication, D1 response handling, synthetic workload construction and extraction; they are not isolated parser CPU or client wall time. Some successful responses had measured CPU above the configured 10 ms limit; the mechanism for those successful responses was not established. The partial sample cannot support reliable percentiles or a maximum across all requests. The official [Pages logs guidance](https://developers.cloudflare.com/pages/functions/debugging-and-logging/) and [workerd trace definition](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/api/trace.c%2B%2B) describe the invocation metrics; the retained record identifies each matched request.

The named aggregate Analytics query was rate-limited; an earlier aggregate labeled `__unknown__` cannot be attributed to this benchmark and is not used. Account-wide quota headroom and billing telemetry remain unknown. The coordinator deleted the temporary tail, new Pages project and new database; before/after inventory records the existing preview and its canonical deployment unchanged, with no Workers subdomain or pre-existing resource changes.

The observed resource failure and CPU samples make this full-document parser, together with its benchmark handling, unsuitable as an assumed Workers Free default. Investigate a bounded streaming approach such as HTMLRewriter and remeasure it under a separately reviewed protocol; this experiment does not establish that an alternative will pass. It also does not pass the full protocol's per-workload sample, maximum, quota-headroom or no-secrets requirements and does not establish merchant accuracy or production readiness.
