# Included-allowance operating policy

The user authorized Workers Paid on November 10, 2026, with the $5/month subscription as the only approved Cloudflare charge. Usage overages, paid add-ons, prepaid credits and external paid APIs are not authorized. Operate below 60% of each included account allowance. This supersedes the earlier Free-only deployment requirement; all other scope and release controls remain. Do not change unrelated Cloudflare services or the frontend.

| --- | ---: | ---: |
| Worker requests | 10,000,000 per billing cycle | 6,000,000 |

These are shared account ceilings, not independent allocations for every project. Subtract other account usage and conservative local reservations; an application may receive a smaller allocation. Storage is a stock and must not reset when the billing cycle changes. AI resets at UTC midnight. Monthly counters use the actual subscription period, not calendar-month assumptions. Storage uses decimal bytes conservatively. Workers/Pages builds, logs, traces and every other product need their own reviewed allowance before activation; they are not implicitly authorized by this table. Runtime logs/traces are disabled in the proposed audit configs. OpenAI, Browser Run, R2, Queues, Workflows, Durable Objects, paid model variants and other integrations remain inactive for this change.

## Implemented safeguards

`backend/allowance-policy.mjs` is the versioned ceiling source. `backend/allowance-store.mjs` uses one conditional SQLite insert and transactional triggers to reserve all requested metrics atomically. Indexed counters replace scans over reservation history. Idempotent retries cannot reserve a different amount under the same identifier. Known completed work appends an idempotent settlement; original reservation history is retained. Unknown usage and timeouts retain their holds. A true multi-connection SQLite test checks contention and all-or-nothing reservations. The user authorized [reservation reconciliation](reservation-reconciliation.md) on November 11, 2026 to remove double counting of completed work without increasing any ceiling.

On November 11, 2026, the user accepted analytics sampling and reporting delay and authorized production admission using the available account data. The Worker collects account-wide Workers request and CPU totals, D1 row totals, D1 storage maxima per database over the preceding 24 hours, and Workers AI neurons for the UTC day. It gets the actual current period from the pinned Workers Paid subscription. Successful empty aggregates become estimated zero in this mode. API failures, malformed responses, invalid scope and unsupported billing windows deny admission.

`backend/analytics-allowance.mjs` caches an explicitly labeled `analytics_estimate` receipt in D1 for five minutes, refreshed on demand. Receipt watermarks in this mode represent collection time. They make no claim about provider completeness or ingestion lag. Counters retain their maximum observed estimate within the relevant cycle or AI day, including concurrent refreshes. Admission takes the greater of the account estimate and a persistent anchored local-completion floor, then adds unresolved holds and the proposed reservation. Completed usage is reconciled against the account estimate rather than added again. Sampling, unreported activity and concurrent unrelated services can still make actual usage higher. A failed refresh denies admission and backs off for 30 seconds. The diagnostic-only local billing collector remains separate and cannot activate production admission.
Service submission, polling and cached-report reads require a successful, nonduplicate allowance reservation before audit database or retrieval work. Both inference runners require the allowance guard. Reports are bounded to 256 KiB. Project configs set the CPU limit to 1,000 ms per invocation and disable runtime log and trace ingestion. The allowance ledger still reserves 2,000 ms per invocation as headroom because Cloudflare allows occasional overruns. This reservation is an estimate. Network timeouts still bound elapsed waits and protect audit completion. Cloudflare excludes network waits from Worker CPU time. [Worker CPU limits](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)

## Billing guarantee boundary

This is a hard application admission policy, not a guaranteed $5 invoice. An inbound request is billable before application admission, and unrelated services consume shared allowances independently. A denied request and a budget-ledger query can themselves consume resources. Delayed billing data cannot provide synchronous account-wide headroom. Do not represent alerts, counters or a successful HTTP response as a billing cap.

Cloudflare budget alerts notify without pausing usage. Its documented spend-policy API covers Workers and Durable Objects, requires a positive cent threshold, and reports asynchronous estimates/enforcement; it does not establish zero-overage protection for all services. [Budget alerts](https://developers.cloudflare.com/billing/manage/budget-alerts/), [spend-policy API](https://developers.cloudflare.com/api/resources/billing/subresources/spend_policies/methods/create/). No billing or unrelated-service settings were changed. The user accepts the analytics limitation for production testing. Failed collection and observed exhaustion still deny admission.

### R2 Standard account estimates

R2 Standard includes 10 GB-month, 1 million Class A and 10 million Class B operations per month; the operating limits are 6 GB-month, 600,000 Class A and 6 million Class B. [R2 pricing](https://developers.cloudflare.com/r2/pricing/) defines storage as the average of daily peaks, and says some failed requests are billable. The R2 guard counts every status, and unknown operation types against both classes. The current storage ceiling is 6,000,000,000 bytes including payload and metadata; keeping every daily peak below it bounds the monthly average, subject to reporting delay and external account activity. Infrequent Access is not covered by the free tier and is not authorized for this pipeline.

The collector needs an account API token with permission to read account R2 metrics (`GET /accounts/{account_id}/r2/metrics`) and account GraphQL analytics (`r2OperationsAdaptiveGroups` and `r2StorageAdaptiveGroups`). [Account metrics](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/metrics/methods/list/) may lag; [R2 analytics](https://developers.cloudflare.com/r2/platform/metrics-analytics/) is adaptive and has no completeness watermark. Collection time is not proof that provider data is current. The accepted estimate therefore cannot guarantee billing limits against delayed or concurrent external account usage. Missing fields, permission failures, truncation, malformed data, and unavailable collection deny admission. The storage endpoint must report both Standard uploaded and published payload and metadata sizes (`payloadSize` and `metadataSize`); after the user enabled R2, a read-only check on November 17, 2026 returned the expected zero-valued shape. The same account returned successful empty R2 operations and storage GraphQL results. The collector also sums each bucket’s maximum payload and metadata over the last 31 days, and uses the greater of that and current account storage; this conservative peak protects against earlier higher usage within the rolling window. After the user updated the token permissions, the existing private runtime token successfully collected all R2 counters on November 17. The user enabled R2 in the dashboard; this implementation performed only read-only account checks. The guard caches a successful collection for less than five minutes per instance.

R2 pricing describes included usage as monthly but does not establish in that page whether its reset matches the Workers subscription period. Until verified, operations are collected over the preceding 31 days, a conservative superset of a calendar month or a standard subscription month. Unknown reservations remain additive across periods; the first account estimate plus completed local usage is compared with later account estimates using the larger value, avoiding counting the same completed work twice. The initial account anchor and completed local reservations remain in the local high-water totals indefinitely, including after deletion. This deliberately favors denial over silently releasing storage whose inclusion in delayed metrics cannot be proved; an operator-controlled, evidence-backed reconciliation mechanism is needed before reclaiming that headroom. This is not an exact invoice meter.
