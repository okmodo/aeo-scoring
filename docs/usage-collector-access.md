# Read-only Cloudflare billing access

For the collector, create a custom API token with **Account → Billing → Read**, limited under Account Resources to the one intended account. Put the token in the collector's private process environment or secret store; do not paste it into chat, commit it, put it in a URL, or record it in logs or evaluation traces. Provide the account ID separately in the private environment. Use an API token rather than a Global API key. Cloudflare's [billing permission guide](https://developers.cloudflare.com/billing/understand/billing-permissions/) specifies that permission for billing API tokens; the [subscription endpoint](https://developers.cloudflare.com/api/resources/accounts/subresources/subscriptions/methods/get/) explicitly accepts Billing Read. Billing Write and Workers edit permissions are unnecessary for these reads.

The intended read-only endpoints are `GET /accounts/{account_id}/subscriptions`, `GET /accounts/{account_id}/billable-usage/info`, and `GET /accounts/{account_id}/billable-usage`. The [v1 info](https://developers.cloudflare.com/api/resources/billing/subresources/usage/methods/get_account_usage_info_v1/) and [v1 usage](https://developers.cloudflare.com/api/resources/billing/subresources/usage/methods/get_account_usage_v1/) references identify API token authentication but do not enumerate endpoint-specific accepted permissions. Thus Billing Read is the documented least-privilege starting point, not proof that this account and each alpha endpoint will accept a token. A 403 must remain a blocked result; do not broaden permissions automatically.

The separate [v2 usage endpoint](https://developers.cloudflare.com/api/resources/billing/subresources/usage/methods/get_account_usage_v2/) is labeled **Alpha, Restricted**. Eligibility may be an additional obstacle; Billing Read does not establish eligibility. Its default date range starts at the calendar month and is limited to 31 days, so it cannot be assumed to match the subscription period. The collector does not need additional analytics or Worker permissions merely to read billing.

## What access does and does not establish

Cloudflare's subscriptions response has optional `current_period_start` and `current_period_end` fields; the relevant subscription must be unambiguously matched and both dates present. The v1 info response gives an anchor and subscription metadata, but its `end_timestamp` is a cancellation time, not the active billing period end. V1 usage records explicitly have no `BillingPeriodEnd`. Their `ChargePeriodEnd` identifies a charge period, not a data-completeness watermark. The v1 reference describes an anchor-day requirement for a date-filtered query; an empty response can therefore mean a range mismatch rather than zero usage. See the [subscriptions](https://developers.cloudflare.com/api/resources/accounts/subresources/subscriptions/methods/get/), [info](https://developers.cloudflare.com/api/resources/billing/subresources/usage/methods/get_account_usage_info_v1/), and [usage](https://developers.cloudflare.com/api/resources/billing/subresources/usage/methods/get_account_usage_v1/) schemas.

No completeness watermark or guaranteed reporting-lag bound was found in those references. A successful read, a recent request, a daily bucket end, or a missing metric does not prove complete current account-wide consumption. The [billable usage dashboard](https://developers.cloudflare.com/billing/manage/billable-usage/) describes usage-based overage charges and Pay-as-you-go eligibility; it is not a guarantee of all included-allowance counters. In particular, a cost of zero is not evidence that usage is zero. Keep optional work paused until every required metric, unit, scope, stock semantics, lag and concurrent account usage have independently adequate evidence and a conservative enforcement mechanism. The project's [60% policy](included-allowance-policy.md) remains the operating limit and is shared with other account usage.

## Access verification

The local read-only verification interface uses `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_SUBSCRIPTION_ID`, and `CLOUDFLARE_BILLING_READ_TOKEN` in the private process environment, with `--db` pointing to a private local SQLite file in a trusted private directory. Its `--fixture` mode uses frozen wire responses offline and does not contact the API. Keep the database, output and environment private; output includes the account ID.

A read-only probe recorded at 2026-11-10 21:42:30 UTC returned HTTP 403 `credential_not_authorized` for each of the three v1 GET paths above with the then-available credential. This establishes neither the token's exact grants nor the account's endpoint eligibility; supply the documented one-account Billing Read token and verify again only through an explicitly authorized read-only run. Never interpret a denial as zero usage.

## Worker admission wiring

The audit entry point uses `AUDIT_DB` and reads the pinned account and subscription from `AUDIT_BILLING_ACCOUNT_ID` and `AUDIT_BILLING_SUBSCRIPTION_ID`. The public build derives these values from `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_SUBSCRIPTION_ID`. Keep the billing token in the local collector environment. The Worker needs only the pinned identifiers and its D1 binding.

Before rollout, the project database needs the allowance tables and a current receipt from a reviewed source. That source must establish coverage and freshness for all six usage metrics, including account activity outside this Worker. The current collector records diagnostic observations and cannot activate a receipt. An audit starts only after the ledger reserves the request against all applicable ceilings. Missing evidence returns `503` and an exhausted allowance returns `429`.
